the 25 Sept submission deadline.

## Confirmed — verified by hand

### 1. BLOCKER — `/pet` fabricates a pet and labels it `live`

`src/app/pet/pet-live-client.tsx:15` and `:95`

`PLACEHOLDER_PET` is a hand-written view model — `displayName: "Mochi"`,
`growthPoints: 0`, `nextStageAt: 20`, and critically `dataMode: "live"`. Line 95
does `registry.pet ?? PLACEHOLDER_PET` and passes the result to `CarePanel`,
which renders its growth line *unconditionally* for every action state
(`src/components/pet/CarePanel.tsx:165-169`).

So when a live read fails, the page renders both of these at once:

> "Pet data could not be loaded. **No preview data is shown.**"
> "**0 growth points. Next stage at 20.**"

The app asserts it is showing no preview data while showing fabricated preview
data labelled `live`. A disconnected visitor takes the same path and sees growth
stats for a pet named Mochi that does not exist.

This contradicts the project's headline invariant in three places at once:
`null`/unknown must never render as `0`; fixtures are never a fallback for a
failed read; and the README's "the UI never shows a number it cannot justify."

**Proof.** Rendering `CarePanel` with `PLACEHOLDER_PET` and the real
`resolveCareActionState({readStatus: "error", hasPet: false, …})` output asserts
both strings present simultaneously — test passes.

**Fix.** Delete `PLACEHOLDER_PET`. Render the no-pet / failed-read branch from
an explicit empty or error state that carries no numbers. If `CarePanel` needs a
pet-shaped prop, make the prop nullable and have the panel omit the growth line
when it is absent — do not synthesise a pet.

### 2. BLOCKER (environment-dependent) — unbounded RPC loop on any chain that is not X Layer

`src/lib/chains.ts:53`, consumed at `src/hooks/useCommunityStats.ts:47` and
`src/hooks/usePetRegistry.ts:93`

`chainFromDeployment` returns the module-level constants for chain ids `196` and
`1952`, but for **any other id** it calls `defineChain({...})` and returns a
brand-new object. Both hooks call it directly in the render body with no
`useMemo`, and put `chain` in their effect dependency array. Every render
produces a new `chain` identity → the effect re-runs → it calls `setCommunity` /
sets pet state → re-render → new `chain` → effect re-runs. Unbounded.

**Proof.** Mounting the real `useCommunityStats` once with a mocked transport:

| Chain id | `readContract` calls in 400 ms |
|---|---|
| 196 (X Layer mainnet) | **1** |
| 31337 (Anvil local) | **7,157** |

~18,000 RPC calls/second from a single mount.

**Blast radius.** X Layer mainnet (196) and testnet (1952) are hardcoded, so the
loop does **not** fire on the submission target — this is not a demo blocker if
you deploy to X Layer. It fires on **local Anvil (31337)**, which is the exact
environment every piece of QA evidence in `docs/qa/` was gathered in, and on any
custom RPC.

**Fix.** Memoise on the primitive fields, not the object:

```ts
const chain = useMemo(
  () => chainFromDeployment(deployment),
  [deployment.chainId, deployment.rpcUrl, deployment.networkName,
   deployment.currencySymbol, deployment.explorerBaseUrl],
);
```

in both hooks. (`useWallet.ts:93` has the same call but does not put it in a
dependency array, so it is not looping — memoise it anyway for consistency.)

### 3. HIGH — a failed read offers a care transaction that bypasses both guards

`src/lib/care-action-machine.ts:89`

`readStatus === "error"` is checked *before* `hasPet` and *before* the cooldown
branch, and it returns `{kind: "error"}`. `CarePanel` renders the `error` state
as an **enabled** "Try care again" button wired to `onCare`
(`CarePanel.tsx:139-148`), which calls `registry.care()` for real.

So when the read has failed — meaning the app does not know whether the user has
a pet or is in cooldown — it still offers to submit a care transaction.

**Proof.** With `readStatus: "error"`, `hasPet: false`, and a cooldown active
until 2099, the resolved state is `error`, the button is enabled, and clicking it
fires `onCare` exactly once — test passes.

The contract will revert (`NoPet` / `AlreadyCaredToday`), so no bad state is
written, but the user pays gas to discover a rule the UI already knew.

**Fix.** Either gate the retry so it re-reads rather than submitting a write, or
carry the last known pet/cooldown state through the error branch and disable care
when either guard is unsatisfied.

### 4. MEDIUM — a successful adopt is announced as a confirmed care

`src/lib/care-action-machine.ts:10`, `src/app/pet/pet-live-client.tsx:59`

`LivePetControllerInput` has no field identifying *which* write is in flight.
`pet-live-client` reads `registry.txKind` (line 41) and uses it for the community
refresh (line 51) but never passes it into `resolveCareActionState`. So an adopt
receipt and a care receipt are indistinguishable: both set `txPhase: "success"`,
which renders "Care is confirmed."

**Proof.** `resolveCareActionState` with the adopt flow's inputs returns
`{kind: "success"}` and `CarePanel` renders "Care is confirmed" — test passes.

**Fix.** Add `txKind` to `LivePetControllerInput`, pass `registry.txKind`, and
return a distinct state (or message) for a confirmed adoption.

### 5. MEDIUM — wallet errors render as ordinary body text

`src/app/globals.css:494`

`.pet-live-error { color: var(--danger); }` — `--danger` is **never defined**
anywhere in the codebase and there is no fallback, so the declaration is invalid
and the colour inherits. Every wallet error surfaced at
`pet-live-client.tsx:181-183` looks like normal paragraph text.

**Proof.** `--danger` appears exactly once in `src/`, as a `var()` consumer;
zero definitions.

**Fix.** Define the token alongside the other semantic colours (light and dark),
or point the rule at the existing error token the CSS modules already use.

### 6. HIGH — a care confirmed on chain is reported as a failure

`src/hooks/usePetRegistry.ts:278`

Confirmed while fixing the above. After `receipt.status === "success"` passes,
the post-receipt `petOf` re-read is **inside the same `try`**. If that read
throws — an RPC blip is enough — control falls to the catch, which sets
`txPhase: "error"` and the message *"Care failed. No progress was awarded."*

The care **did** succeed on chain. The user is told the opposite, and will
likely retry, which the contract then rejects with `AlreadyCaredToday`.

This is QA checklist item **I10** ("Confirmation succeeds but refresh fails →
Transaction truth and stale/unavailable display are distinguished") inverted.

**Fix.** Wrap the re-read in its own `try`/`catch`. On failure keep
`txPhase: "success"` — the write is confirmed — and mark the snapshot
`readStatus: "error"` with a message saying the action confirmed but the
refresh failed, so the display is flagged stale rather than false.

### 7. HIGH — a write that lands after an account switch is applied to the new wallet

`src/hooks/usePetRegistry.ts:293`

Confirmed while fixing the above. The read effect has a `cancelled` flag, but
`runWrite` has no equivalent. It captures `address` in its closure and, after
awaiting a receipt and a re-read, calls `setSnapshot(...)` unconditionally. If
the user switches accounts mid-transaction, wallet A's pet is written into
state while wallet B is connected.

This is QA checklist item **I8** ("Switch wallet or chain → Previous identity's
cached pet is not presented as current").

**Fix.** Track the identity cache key in a ref, capture it when the write
starts, and bail out after every await if it no longer matches.
